## Qué se hizo

### 1. Validaciones SQL automáticas (deuda #3 de technical-debt)

**Hallazgo clave de descubrimiento:** las validaciones viven en
`database/migrations/validation/*.validation.sql` (001–018), **no** en `database/validation/`
como asumía el brief (esa ruta no existe). Además **no son autocontenidas contra el esquema
final**: cada una valida el estado *inmediatamente posterior a su propia migración*
(006 usa `matriculas.grado_id` que 008 normaliza; 007 usa `usuarios.rol` que 010 retira;
008 espera índices que 016 renombra) y el fixture comparte datos legacy. Ejecutarlas tras
aplicar todas las migraciones (enfoque inicial) **falla**.

- `ValidationRunner.cs` (nuevo): crea su **propio Postgres desechable** (Testcontainers),
  aplica el bootstrap base (`SupabaseSecurityBootstrap` + `LegacySchemaBootstrap`, misma
  secuencia del fixture, **sin inyectar datos legacy**), luego para cada migración n aplica
  `MigrationRunner.ApplyUpToAsync(n)` y ejecuta `NNN_*.validation.sql`. Contrato:
  **pasa ⇔ no lanza error SQL y ninguna consulta devuelve filas**; si algo falla → lanza
  `ValidationFailedException` con detalle por archivo.
- `MigrationRunner.ApplyUpToAsync(N)` (nuevo): aplica 001→N (núcleo compartido con
  `ApplyActiveAsync`), necesario para la validación incremental.
- `MigrationValidationSuiteTests` (nuevo, 2 tests): positivo (secuencia incremental completa
  pasa sobre base limpia) + negativo (una validación ad-hoc que devuelve filas hace fallar el
  mecanismo → cubre «falle si cualquier validation falla»). **2/2 PASS**.
- `PostgreSqlFixture.cs`: **revertido** a su estado original (sin hook de validaciones) — las
  validaciones ya no corren en el fixture, corren en `MigrationValidationSuiteTests`.
- Validaciones 001–018 **normalizadas al contrato «0 filas = pasa»**: reescritas 001/002/003/007
  (eran informativas/`count(*)`/listings); 008–016 y 018 ajustadas a `where not exists`
  (registro final convertido a fallo). 004/005/006/017 ya conformes.
- Nota: `019` no tiene aún `validation/019_*.validation.sql`; la suite incremental la aplicaría
  si existiera. No se creó (la 019 se validó exhaustivamente en la Fase 020 con tests
  multitenancy) — registrar como pendiente opcional.

### 2. Checksum SHA-256 en `schema_migrations` (deuda #4 de technical-debt)

**Hallazgo:** `schema_migrations` **ya tiene la columna `checksum text null` desde la migración
001** → no hace falta migración nueva. 007–019 auto-insertan su fila; 001–006 no; ningún
rollback toca la tabla.

- `MigrationRunner`: tras aplicar cada migración **solo hace `UPDATE` a filas existentes**
  (nunca `INSERT`, para preservar la simetría rollback/reapply de `RollbackTests`), almacenando
  el SHA-256 (`Convert.ToHexStringLower`) del contenido. **Backfill** de filas históricas con
  `checksum IS NULL` (no bloquea instalaciones antiguas; queda verificado hacia adelante).
- Si una migración ya aplicada cambió (hash distinto) → `MigrationChecksumMismatchException`
  con mensaje explícito «migración modificada».
- Fix de lectura: `ReadStoredChecksumAsync` maneja `DBNull` → null (no lanza cast).
- `ChecksumMigrationTests` (nuevo): registra hash; archivo intacto pasa; contenido modificado
  falla; backfill de NULL; secuencia 001→última con checksum. **10/10 PASS** (junto a
  `MigrationTests` + `RollbackTests`).

### Fix adicional (hallazgo en la suite DB)

`CargosMultitenancyTests` (Fase 020) fallaba con `total_vencido` esperado 0 / obtenido 400 en
main **sin** cambios 020.5A (confirmado con stash). Causa: dependía de `current_date` de la DB
(contenedor Postgres en **UTC**) pero fijaba `cicloInicio = DateTime.Today` del **host (CST)**;
al cruzar medianoche UTC la cuota que vence "hoy" quedaba vencida por 1 día. Fix: anclar
`cicloInicio` al `current_date` de la DB (determinista, no depende de la TZ del host). No toca
migración ni RPC.

## Decisiones de diseño

- Validaciones → **incrementales** (aplicar 001→n, validar n) en Postgres limpio, no en el fixture.
- Checksum → UPDATE solo filas existentes (nunca INSERT), backfill NULL, fail en divergencia.
- Cobertura backend → en el proyecto de tests de la API (referencia el backend real).
- Cobertura frontend → lcov vía builder `@angular/build:unit-test` + `@vitest/coverage-v8`.
- SonarCloud → generación en CI sí; import como paso manual (no rompe pipeline sin token, no
  desactiva Automatic Analysis, no expone secreto).
